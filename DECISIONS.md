# Tipwell decisions

This file records implementation assumptions made while building v1. The product prompt is the source of truth for requirements; these notes document choices where the prompt left more than one reasonable implementation.

## Product and UX

- The repository's existing product name, **Tipwell**, is retained even though the prompt calls the working name Tipwise.
- The home route is the diner calculator and does not require authentication or a network request for calculation.
- Worker tools live at `/worker` and remain usable without an account. The shift log, export, workplaces, and settings require an account.
- The default region is US and the default currency is USD. Canada is the only other region in v1, with CAD as its regional default. Currency can be overridden in account settings.
- The region selector changes display defaults only; no tax, legal, or currency-conversion rules are encoded.
- The default tip percentage is 18% because it is a neutral middle preset for this product. The visible diner presets are 15%, 18%, and 20%, with custom input available.
- The calculator stores its browser preferences under `tipwell:diner-state`. Browser preferences are merged into an account after sign-in only when that account has no saved settings; persisted account values win thereafter.
- The Advanced decoder is collapsed initially and remembers its open state. It is a panel on the home route rather than a separate page.
- A simple system `prefers-color-scheme` media query provides dark mode. There is no separate theme preference in v1.
- The app uses plain browser controls and no external font or analytics dependency to keep the first screen fast and private.

## Money and calculation behavior

- All stored monetary values are integer cents. `src/lib/calc/money.ts` is the shared boundary for parsing, half-up rounding, summing, and formatting.
- User-entered fractional cents are rounded half-up. Display formatting uses `Intl.NumberFormat`; division by 100 occurs only at the presentation boundary.
- `pre_tax` means items subtotal minus discount. `pre_tax_plus_fees` adds the explicit fees field. `pre_discount` means the original items subtotal before discount. `post_tax` means the discounted items subtotal plus explicit fees and tax.
- An included service charge is deliberately excluded from the normal tip bases. It has its own warning and combined effective-rate display so users can decide what to do without silently tipping on the charge.
- When tax is entered as a rate, it is calculated on the post-discount amount before explicit fees and rounded to cents once.
- “Effective food percentage” means the calculated tip divided by the original items subtotal, not divided by the selected base.
- A total round-up adds the smallest non-negative amount needed to reach the next whole dollar. A per-person round-up first performs the exact even split, then rounds each person's share up to a whole dollar; every added cent is attributed to the tip.
- Even split leftovers are distributed one cent at a time from the first person forward. This makes the result deterministic and guarantees the shares sum exactly.
- Pool split uses largest remainder, with equal remainder ties resolved by input order. An optional pool tip-out is removed before shares are allocated.
- Worker rates may be fractional cents internally because a rate is a quotient, but displayed rates are rounded half-up. Zero hours returns a safe zero from the calculator and an unavailable (`—`) average in shift summaries.
- Decimal shift hours are stored as hundredths of an hour (`hoursX100`). Input beyond two decimal places is rounded half-up before storage.

## Persistence, auth, and data ownership

- Better Auth owns the `user`, `session`, `account`, and `verification` tables. The checked-in `src/db/auth-schema.ts` is generated by the Better Auth CLI and is not treated as application schema.
- Application tables use Better Auth's text user id. `user_settings` stores region, currency, default tip basis points, default tip base, worker mode, plan, and `updatedAt`.
- Google sign-in is enabled only when both Google environment variables are present. Email/password remains available without Google configuration.
- Server environment values are validated with Zod at server entry points. Secret values are never included in validation errors. Missing credentials are a setup error, not a reason to silently use a production default.
- Every shift and workplace read/write includes the authenticated user id. A workplace referenced by a shift is looked up with both its id and user id before insertion or update.
- `workplaceId` is nullable and is set to null when its workplace is deleted; shift records remain available.
- The `plan` column defaults to `free`. Billing is not implemented, and `canUseFeature` returns true for every v1 feature so the entitlement seam can be replaced later.
- Settings API writes accept partial updates but never allow clients to update `plan`. Local browser settings can be submitted as `localSettings` during the first account update.
- No live database credentials are stored in the repository. Migration generation is checked locally; applying migrations requires the operator's Neon connection string.

## Shift records and exports

- `serviceChargeShareCents` is a first-class shift column. It is labeled “Service charge / auto-gratuity share (paid by employer)” in the UI, remains separate in CSV, and is never included in `totalTipsCents` or `netTipsCents`.
- Employer-paid service-charge share is included in total compensation and average real hourly rate because it is wage-like compensation for the worker record. This is a record-keeping choice, not tax advice.
- Optional sales values are stored as nullable cents. Missing sales are represented as blank CSV cells rather than zero so “not recorded” stays distinct from “zero.”
- CSV exports contain one column per shift field plus the resolved workplace name. Dollar fields are exported as two-decimal strings, dates use ISO `YYYY-MM-DD`, and values containing commas, quotes, or line breaks are escaped according to CSV conventions.
- Date-range bounds are inclusive. Missing bounds mean all records available to the authenticated account.
- Weekly grouping uses Monday as the week start. Monthly and YTD summaries use the browser's current calendar year; the displayed currency is currently the account's regional/default currency.
- The shift log has a visible “Record-keeping only. Not tax advice.” note and avoids hardcoded tax rules or deductions.

## Delivery and known gaps

- The service worker uses a small cache-first shell for the calculator and caches successful GET responses. It does not attempt to make authenticated shift actions offline.
- A live Neon/auth smoke test was not possible without credentials in this workspace. `pnpm lint`, `pnpm test`, `pnpm typecheck`, `pnpm build`, and `pnpm db:generate` are the local evidence; `pnpm db:migrate` still requires a reachable database.
- Lighthouse was not run because this environment does not provide a browser-backed Lighthouse audit. The implementation avoids heavy client dependencies and external assets, but the target score still needs measurement in CI or a local browser.
- The v1 settings endpoint is wired and the sign-in page merges browser calculator preferences, but the home calculator continues to use its local state for immediate no-account operation. A later sync layer can hydrate it from account settings without changing the calculation APIs.
- Account deletion, email verification flows, password recovery, billing, multiple currency conversion, and employer dashboards are intentionally outside v1.
